# 手法と、2025年版からの改良点（宣言）

本記事は、2025年に公開した
「日本語アナライザーの比較（Kuromoji / Sudachi / MeCab / LLM の性能検証）」の続編です。

前回と同じことを繰り返すのではなく、2026年時点でのより良いやり方を提示します。
そのため、テキストもコードも前回と完全に同一ではありません。
どこを、なぜ変えたのかを、ここで明確に宣言します。

> 重要な前提：本記事は「去年と全く同じ条件での定点観測」ではありません。
> 同一条件での厳密な数値比較ではなく、「1年後に、より良い方法で測り直す」ことが目的です。
> したがって、本記事の数値を2025年版の数値とそのまま引き算しないでください。

---

## 実験のスコープ

最初に、何を見て、何を見ないのかをはっきりさせます。
読者の期待値をそろえるためです。

本記事で比較すること：

- 形態素解析器としてのトークン分割。
- 検索インデックス用トークンとしての使いやすさ。
- 専門用語・英数字・単位表現（例: NSAIDs、300〜500mg）の保持。
- 実際の検索クエリに対するヒットのしやすさ。

本記事では厳密な評価対象としないこと：

- 大規模コーパスでの検索ランキング評価。
- 人手による関連度判定（relevance judgment）。
- LLM を Elasticsearch のアナライザーとして使う構成。

---

## 実行環境による違い（重要）

日本語アナライザーは、Elasticsearch の実行環境によって使い方が変わります。
ここを誤解すると「Kuromoji が見つからない」「Sudachi が入れられない」となります。

- Self-Managed（オンプレミス等）：
  各ノードに `analysis-kuromoji` などのプラグインをインストールし、ノードを再起動して使います。
  外部プラグイン（Sudachi など）も導入できます。
- Elastic Cloud Hosted：
  対応していれば外部プラグインを利用できる場合があります。事前に確認してください。
- Elastic Cloud Serverless：
  Kuromoji などの core analysis plugin は bundled（最初から利用可能）です。
  ただし、外部プラグインのアップロードや、Kuromoji 用のカスタム辞書ファイルの追加はできません。

本記事の Sudachi など外部プラグインの実験は、
Self-Managed、または導入可能な Elastic Cloud Hosted 環境で行います。
Serverless 上で外部プラグインを直接使う構成は対象外です。

## アナライザーの「立場」の違い

すべての形態素解析器を同じ枠で語ると誤解を生むため、最初に整理します。

### Kuromoji（Elastic 公式の Japanese analysis plugin）

- Kuromoji は Elastic 公式の Japanese analysis plugin です。
- Self-Managed では各ノードに `analysis-kuromoji` を入れ、再起動して使います。
- 「Kuromoji search analyzer」という名前の標準アナライザーがあるわけではありません。
- 標準の `kuromoji` アナライザーは、次の要素のチェーンです。
  - CJKWidthCharFilter（全角・半角の調整）
  - `kuromoji_tokenizer`
  - `kuromoji_baseform`（活用語を基本形に戻す）
  - `kuromoji_part_of_speech`（助詞・助動詞などの機能語を除去）
  - `ja_stop`（日本語ストップワード）
  - `kuromoji_stemmer`
  - `lowercase`
- 本記事では、標準の `kuromoji` アナライザーと、
  `kuromoji_tokenizer` の `mode: search` を明示したカスタムアナライザーを比較します。
- 補足：`mode: search` はアナライザーの名前ではなく、`kuromoji_tokenizer` の設定です。
  search モードは長い複合語を検索向けに分解します。
  例として `関西国際空港` を、関西 / 関西国際空港 / 国際 / 空港 のように出します。

### Sudachi（外部プラグイン：Works Applications）

- Sudachi は Elastic 公式の機能ではありません。
- Works Applications が公開する `elasticsearch-sudachi` プラグインとして利用します。
- A / B / C の3つの分割モードを持ちます。
- 注意：利用前に、対応する Elasticsearch バージョンを必ず確認してください。
  さらに、Elasticsearch のバージョンだけでなく、実行環境が外部プラグインの導入を
  許可しているかも確認します。
- 特に Elastic Cloud Serverless では外部プラグインを追加できないため、
  Serverless 上で Sudachi プラグインを直接使う構成は対象外とします。

### MeCab / Janome / Lindera

- 本記事では、MeCab / Janome / Lindera を Elasticsearch 公式プラグインとしては扱いません。
- 比較のため、Python 側で事前にトークン化し、その結果を Elasticsearch に投入する方式で確認します。

## 改良点の一覧（2025年版との違い）

### 1. 正規化を「入口」でそろえる

- 方針：すべてのアナライザーに渡す前に、Python で
  `unicodedata.normalize("NFKC", text)` を一度だけ適用します。
- 同じ正規化済みテキストを、全アナライザーに渡します。
- なぜ Python 側でそろえるのか：
  Elasticsearch だけアナライザー内部（ICU の `icu_normalizer` など）で正規化し、
  MeCab / Janome / Lindera は外側で正規化する形にすると、
  比較条件が読者に伝わりにくくなります。
  入口で1回だけそろえるほうが公平で、説明もしやすいです。
- 補足：実運用では、Elasticsearch のアナライザー内で正規化する選択肢もあります。
  公式でも、Kuromoji は全角文字で予期しないトークンを出す可能性があるため、
  `icu_normalizer` キャラクターフィルターを追加する例が紹介されています。
  ICU の `icu_normalizer` は nfc / nfkc / nfkc_cf などを指定できます。

### 2. 機能語の除去を「品詞ベース」に統一する

- 2025年版：トークン化のあと、Python 側で手書きのストップワード一覧を使って除去していました。
- 2026年版：
  - Kuromoji / Sudachi は、アナライザー内部のフィルターで機能語を除去します。
    Kuromoji は `kuromoji_part_of_speech` + `ja_stop`。
    Sudachi は `sudachi_part_of_speech` + `sudachi_ja_stop`。
    これは実際の検索システムの挙動そのものです。
  - MeCab / Janome / Lindera は、各ツールの品詞情報を使って除去します。
    対象は助詞・助動詞・記号・補助記号・接続詞などで、ES 側のフィルターと同じカテゴリにそろえます。
- なぜ改良なのか：
  ツールごとにバラバラな手作業リストではなく、共通の品詞カテゴリで判断するため、
  比較条件がそろい、再現しやすくなります。

### 3. Kuromoji を「正解」として固定しない

- 2025年版：「Kuromoji との類似度（Jaccard）」という1つの数値だけで比較していました。
  これは暗黙に Kuromoji を正解扱いするものでした。
- 2026年版：次の見方を併用します。
  1. トークン数（生／クリーニング後）。
  2. 全アナライザー間のペアワイズ一致率（Kuromoji だけを基準にしない）。
  3. 専門用語がどう扱われたかの定性分析。
     例：アセトアミノフェンは1語のまま残るか。NSAIDs は保持されるか。300〜500mg はどう分割されるか。
  4. 実際の検索クエリでの動作確認。
- なぜ改良なのか：
  トークンが似ていることと、検索で目的の文書が見つかることは別です。
  例えば `関西国際空港` を1語にするか、関西 / 国際 / 空港 に分けるかで、再現率（recall）が変わります。
  読者が本当に知りたいのは「トークンが美しいか」ではなく「探したい情報が見つかるか」です。

### 4. 実際の検索クエリでの動作確認を追加する

- インデックスに少数の文書を登録し、クエリごとに「期待する文書を拾えるか」を確認します。
- クエリと期待ヒットの例（あらかじめ正解を決めておく）：
  - `空港` → `関西国際空港` を含む文書がヒットするか。
  - `関西空港` → `関西国際空港` を含む文書がヒットするか。
  - `NSAIDs` → 英字の専門語が保持され、検索できるか。
  - `300mg` → 数値と単位が検索可能か。
  - `アセトアミノフェン` → 医療系の専門語が1語として保持されるか。
- これは単なるトークン比較ではなく、「検索として役に立つか」まで見るための指標です。
  ビジネス的にも、最終的に効くのは検索のヒット率です。

### 5. LLM は「アナライザー比較」ではなく「参考枠」として扱う

- LLM によるトークン化は、Elasticsearch の転置インデックス用アナライザーとは目的が違います。
- そのため、Kuromoji / Sudachi / MeCab / Janome / Lindera と LLM を横並びにして
  「どれが良いアナライザーか」とは比較しません。読者が混乱するためです。
- LLM は別カテゴリとして、次の観点だけ見ます。
  - 専門語を「意味のまとまり」として拾えるか。
  - 検索の補助（キーワード抽出・意味理解）に使えそうか。
- 注意（よくある誤解）：
  LLM の tokenizer そのものと、LLM によるキーワード抽出・意味単位の分割は別物です。
  tokenizer 自体は、同じモデル・同じ tokenizer・同じ入力なら基本的に同じ結果になります。
  非決定的になりやすいのは、「重要語を抽出して」などと依頼したときの生成結果です。
  生成結果は temperature やモデルのバージョンの影響を受けるため、
  再現性のために、モデル名・プロンプト・temperature を記録します。

### 6. 再現性のためのバージョン記録

実行時に、最低限つぎの情報を結果ファイルに記録します。
これがあると、さらに1年後に本当に再比較できます。

- Elasticsearch のバージョン。
- プラグイン一覧（`GET _cat/plugins?v` の結果）。
- 使用したアナライザー設定（settings JSON）。
- Kuromoji プラグインのバージョン。
- Sudachi プラグインのバージョン。
- Sudachi 辞書のバージョン。
- MeCab 辞書のバージョン。
- Janome / Lindera ライブラリのバージョン。
- Python のバージョン。
- 入力テキスト（データセット）のハッシュ。
- LLM のモデル名。
- LLM へのプロンプト。
- LLM の temperature。
- 実行日。
